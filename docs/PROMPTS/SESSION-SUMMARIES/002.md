## Summary

Pre-implementation hardening session. The goal was to make the specs bulletproof for an unattended overnight build. Started by designing a testing strategy, then made two significant architectural decisions: dropping JSON API routes entirely (MCP tools call the service layer directly) and using POST for all web mutations (no method override). The bulk of the session was three rounds of cross-spec audits, each finding progressively smaller issues until the specs were clean.

The most impactful decision was removing the JSON API routes. Blaine pushed back on keeping them "for testing convenience" — correctly identifying that testing redundancy as a code smell. This led to restructuring tests around service layer tests (the workhorse) and lightweight web route smoke tests, which is a cleaner architecture overall.

## Decisions

1. **Testing strategy:** Integration tests only (no E2E/Playwright). Service layer tests for business logic, Fastify `.inject()` for web route smoke tests. Vitest with real SQLite.
2. **No JSON API routes:** MCP tools call service functions directly. No redundant HTTP/JSON layer. Service tests are the contract tests for both web routes and MCP.
3. **POST for web mutations:** No method override. `POST /worlds/:id/update` and `POST /worlds/:id/delete` for web forms. API stays RESTful in MCP.
4. **Named function exports:** Services export `createWorld`, `listWorlds`, etc. — not `worldService.create`. Consistent across all specs.
5. **Prisma singleton, no DI:** Single `PrismaClient` in `src/db.ts`, env var controls which database. Tests set `DATABASE_URL=file:./test.db` inline.
6. **globalSetup/globalTeardown:** Migrate reset once per test run (not per file), Prisma disconnect only in globalTeardown.
7. **Sequential test execution:** Shared SQLite DB means no parallel test files.
8. **Lore status route returns JSON:** The one exception to "web routes return HTML" — inline JS fetch for snappy keep/discard.

## Insights

- Removing the API routes simplified everything downstream: fewer tests, cleaner architecture, no confusion about which interface to use. The "but we need it for testing" argument was a trap — testing the service layer directly is better.
- Three audit passes was the right number. First pass found structural inconsistencies (DI contradiction, stale API references). Second found lifecycle issues (Prisma disconnect, globalSetup location). Third found only minor naming and documentation gaps.
- The user's instinct to question redundancy ("who uses the API routes? is that different from MCP?") led to the best architectural decision of the session.
