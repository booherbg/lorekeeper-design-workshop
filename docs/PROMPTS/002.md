## 2. No E2E Testing (05:06 UTC)

> should we spin up end to end testing to make sure we aren't missing anything too wild?

**What happened:** Decided against Playwright/E2E — adds dependency complexity and flakiness that kills unattended runs. `.inject()` already hits the full stack. E2E remains a stretch goal.

<details>
<summary><strong>Response:</strong> For base scope, I'd say no. Here's why:</summary>

For base scope, I'd say no. Here's why:

**Cost vs. value:** Playwright/Cypress adds a real dependency chain — browser binaries, config, flaky waits, CI complexity. For a server-rendered CRUD app where `.inject()` already hits the real database and returns real responses, E2E catches very little that integration tests miss. The gap is basically "does the HTML render in a browser" and "do form submissions actually POST" — both of which are Handlebars + standard HTML, not dynamic JS that could silently break.

**The one place E2E would matter:** Slice 5's inline lore keep/discard buttons (vanilla JS fetch). That's the only client-side interactivity in the whole base project. When we get there, we can add a small manual test checklist or a targeted browser test if it feels risky.

**For the overnight run specifically:** E2E tests are the #1 source of flaky failures that stop an automated run cold. Integration tests with `.inject()` are deterministic — SQLite, no network, no browser. Much better for unattended execution.

The build plan already calls E2E a stretch goal, and I agree with that call. Let's keep the testing spec tight:

- **Integration tests** (`.inject()` + real SQLite) for all routes
- **Validation coverage** for edge cases at the HTTP boundary
- **Manual smoke test** in the browser at each slice boundary when you're at the keyboard

Want me to write this up as a testing spec in `docs/SPECS/` so it's captured alongside the other specs?

</details>

## 4. POST for Web Mutations (05:09–05:10 UTC)

> thats fine

> whats idiomatic? fastifly certainly has a pattern for this

**What happened:** No established Fastify method-override pattern. Went with POST for all web mutations (`/update`, `/delete` suffixes). API-style PUT/DELETE only in MCP.

<details>
<summary><strong>Response:</strong> Honest answer: Fastify doesn't have a strong convention here the way Rails does with `Rack::MethodOverride`. There's no official `@fastify/method-over</summary>

Honest answer: Fastify doesn't have a strong convention here the way Rails does with `Rack::MethodOverride`. There's no official `@fastify/method-override` plugin. The ecosystem is API-first — clients send real PUT/DELETE, so it's never been a big concern.

The patterns I've seen in Fastify server-rendered apps:

1. **Custom preHandler hook** — parse `_method` from the form body, rewrite `request.method`. ~10 lines. Works but it's DIY.
2. **POST routes for web mutations** — separate web route registration with POST for create/update/delete. Most common in practice for Fastify + templates projects.

The build plan actually listed `@fastify/formbody` with a `_method` field, but that plugin just parses `application/x-www-form-urlencoded` bodies — it doesn't do method rewriting.

Given there's no blessed Fastify pattern: let's go with **POST routes for web, PUT/DELETE for API**. It's the path of least resistance, no custom plumbing, and it's what most Fastify SSR apps actually do.

Web routes would look like:
- `POST /worlds` — create
- `POST /worlds/:id/update` — update
- `POST /worlds/:id/delete` — delete

API routes stay RESTful:
- `POST /api/worlds` — create
- `PUT /api/worlds/:id` — update
- `DELETE /api/worlds/:id` — delete

I'll update the API endpoints spec to reflect this. Want to commit the testing spec + that update together before we start building?

</details>

<summary><strong>Response:</strong> You're right to push on that. Let me think about this differently.</summary>

You're right to push on that. Let me think about this differently.

The MCP server calls service functions directly. The API routes call the same service functions over HTTP. They're not redundant for *testing* — they're redundant, period. And we're using the redundancy to justify testing convenience.

Better approach: **test the service layer directly**.

```typescript
describe("WorldService", () => {
  it("creates a world with valid input", async () => {
    const world = await worldService.create({ name: "Eldoria", description: "..." });
    expect(world.name).toBe("Eldoria");
  });
});
```

Then for web routes, we keep the lightweight `.inject()` tests — status codes and redirects. The service tests cover business logic, the web route tests cover HTTP behavior. No API routes needed as a test intermediary.

This also means:
- **Fewer routes to build per slice** — cuts the work roughly in half for each entity
- **MCP tools are the programmatic interface** — no confusion about which JSON endpoint to use
- **Service layer is the real contract** — tested directly, used by both web routes and MCP tools
- **Validation lives in the service layer** — not duplicated between API and web route handlers

I'd update the testing spec and API endpoints spec to drop the JSON API routes entirely. Web routes for humans, MCP tools for Claude, service layer tests for correctness.

Want me to make those updates?

</details>
